## ConcreteAsyncVaultImpl

Vault implementation with epoch-based asynchronous withdrawals. Withdrawal
        requests are queued and settled when an epoch closes rather than executed
        immediately against vault liquidity.

_Extends `ConcreteStandardVaultImpl`; users interact with it through a `VaultProxy`._

### _upgrade

```solidity
function _upgrade(uint64, bytes) internal virtual
```

_Upgrade hook for vaults migrating to this implementation.

All upgrade-time work (legacy role migration + idempotent async-specific state
init gated on `latestEpochID == 0`) is delegated to `StateInitLib` to keep the
runtime bytecode of this contract — and of `ConcreteBridgedAsyncVaultImpl`,
which inherits it — under the EIP-170 limit. The library runs in the proxy's
storage context via DELEGATECALL._

### closeEpoch

```solidity
function closeEpoch() external virtual
```

Closes the currently open epoch so it can be processed.

_Caller must hold `WITHDRAWAL_MANAGER` and the vault must not be paused. Once closed, no
     additional requests can be added to that epoch; the next `processEpoch` call settles it._

### processEpoch

```solidity
function processEpoch() external virtual
```

Process all pending redeem requests for a specific epoch

_Harvests all strategies to get current accurate pricing before processing

Can process any epoch with pending requests, enabling historical processing
Only callable by WITHDRAWAL_MANAGER role_

### processPartialEpochRequest

```solidity

```

Fulfil all or part of a user's withdrawal request from a closed,

_Burns the specified shares at the current exchange rate and transfers the
     corresponding assets immediately (no separate claim step).  The epoch is
     NOT marked as processed; `processEpoch()` must still be called to
     finalise the epoch.
Only callable by WITHDRAWAL_MANAGER role._

#### Parameters

| Name | Type | Description |
| ---- | ---- | ----------- |
| user | address | The user whose closed-epoch request to fulfil. |
| epochID | uint256 | The closed epoch to target. Must be closed and not yet processed                (intent-validation parameter). |
| amount | uint256 | Number of shares to process. Pass `type(uint256).max` to process               the user's entire request. |

### allocate

```solidity
function allocate(bytes data) public virtual
```

Executes fund allocation and deallocation operations across multiple strategies.

_This function performs a yield accrual operation first to update vault accounting,
     then executes the allocation operations specified in the data parameter.
All operations are performed via delegatecall to the respective modules to maintain
     proper storage context and access control.
Only callable by accounts with the ALLOCATOR role.
The function automatically triggers yield accrual before allocation to ensure
        accurate vault accounting prior to fund movements._

#### Parameters

| Name | Type | Description |
| ---- | ---- | ----------- |
| data | bytes | ABI-encoded array of AllocateParams structures containing the allocation             operations to execute. Each param specifies whether to allocate or deallocate             funds, which strategy to use, and any additional data required by the strategy. |
